**PASS** — the two 413 paths answer identically whether the container or the service refused, and the two
validation branches are distinguished by the field name each can produce (`page` from a handler parameter,
`requestedCount` from a `@Validated` bean's argument), so neither test can pass through the wrong handler.

## 3. Nothing internal leaves the process

Every one of the fifteen tests asserts the absence of an exception name, `at com.`, `org.springframework`,
`java.`, a file path and SQL in the body — the check the security rules demand and the DoD asks to verify
rather than assume. The 500 path is the one that matters: the stack trace goes to the log line, the body
stays a single sentence.

## 4. The container's refusal reaches the advice, not Tomcat's error page

`MultipartUploadCeilingTest` drives real multipart requests through Tomcat and now also asserts
`code == "upload-too-large"` and `Content-Type: application/problem+json` on both 413 cases. Without an
explicit mapping, an oversized request would be answered by the container's default error page before any
controller advice ran — this is the only test that can tell the difference.

## 5. Spec gap found while implementing (recorded, not patched)

`_docs/openapi.yml` documents **no error schema at all** — across 163 lines the only mention of a failure is
one `'400'` description on `POST /dumps`, with no shape and no `code`. The codes and statuses above therefore
come from `.claude/rules/backend.md` ("`ProblemDetail` … plus a stable `code`") and ADR-011, not from the
contract of record. That is a gap in the contract rather than a deviation from it, and `_docs/` is read-only:
closing it needs the owner's approval and an ADR. Recorded here and in `backend/README.md` so it is visible at
release time instead of being rediscovered.

**Not covered / SKIPPED**
