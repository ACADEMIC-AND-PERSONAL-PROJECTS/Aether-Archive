`curl --path-as-is`, so the request line reaches the server exactly as written. "clean" means the body
contains neither the canary, `/etc/passwd`, nor the data-directory path.


`404` is the archive's own problem+json; `400` is Tomcat refusing the request line before Spring sees it.

**Self-validating pair** — proves the client sent the path as written and that the refusals are containment
rather than a blanket refusal:

## 3. Probe — directories are never listed

The refusal names the instance, never a filesystem path — the leak this story could plausibly introduce.

## 4. Probe — media type comes from the stored extension

| Stored name | Answer | | Stored name | Answer |
| --- | --- | --- | --- | --- |
| `.png` | `200 image/png` | | `.webp` | `200 image/webp` |
| `.jpg` | `200 image/jpeg` | | `.avif` | `200 image/avif` |
| `.jpeg` | `200 image/jpeg` | | `.xyz` | `200 chemical/x-xyz` |
| `.gif` | `200 image/gif` | | `.html` | `200 text/html` |

Every extension the upload path can write has its own media type — nothing falls through to
`application/octet-stream`, so no second whitelist was needed. `Accept: image/jpeg` and `Accept: text/html`
both still get `image/png` for a stored `.png`: the request does not decide the type. `HEAD` on a stored file
→ 200 with the same headers; `Origin: http://localhost:5173` → `Access-Control-Allow-Origin` echoed, which
the colour extraction in E2-S4 will need.

## 5. Probe — a symlink inside `images/` is followed out of the data directory

Created by hand on the filesystem, not by any request:

```
link -> file outside images/ : 200  AETHER-CANARY-OUTSIDE-IMAGES
dir  link -> outside images/ : 200  AETHER-CANARY-IN-AN-OUTSIDE-DIRECTORY
link -> /etc/passwd          : 200  root:x:0:0:...        (md5 matches /etc/passwd)
the same bytes at a plain path /images/passwd : 404
```

Spring's containment check reads the URL (it stays under the location prefix), so a link that resolves
elsewhere passes it. **Not reachable by any request** — 46 hostile paths, a hostile client filename and
encoded separators were all refused — so this is hardening, not a defect, and it is routed to **E6-S17**
(issue #79) rather than patched inside a serving story.

The review widened the finding, and the widening matters more than the original: **with `images/` itself a
link** to a directory outside the data directory, the boot succeeds and writes its own write-probe *through*
the link, reads follow it, and uploads are refused with `500 storage-failure`. The actor there is an operator
— a `cp -a`/`rsync -a`/tarball restore, or a manual link into a synced folder — not someone with a shell in
`images/`, which is why E6-S17 is `p1`: the file-level link needs a writer inside the directory, but this one
does not. ADR-012's guarantee holds for uploads and says nothing about the boot.
