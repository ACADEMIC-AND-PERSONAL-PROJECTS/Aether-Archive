## 4. What changed

`support/PostgresTestConfiguration` no longer hands Spring a `@ServiceConnection` container bean. It starts
one `postgres:17-alpine` container in a static initialiser — shared by every context in the JVM — and
exposes a `JdbcConnectionDetails` bean whose URL points at the database the context asked for
(`@Value("${aether.test.database:test}")`). The database is created once per name; PostgreSQL's `42P04`
(`duplicate_database`) is the only error the creation tolerates, so two contexts naming the same database
still share it.

- **One container, one database per context.** The isolation the suite had is unchanged — the flow classes
  delete every row or add a test-only Flyway migration, and either would corrupt the repository slices,
  whose assertions are about the whole archive (`DumpQueryTest` reads every dump there is, and
  `DumpService.sixPhotosOf` makes a dump that lost photos answer 500). Databases are cheap where containers
  were not.
- Six classes name their own database with `@TestPropertySource`: the two flow classes, the two test-only
  migration classes, and — with the same name in all four, so the four keep sharing one context and one
  schema — the repository slices.
- `@ServiceConnection` was rejected, not overlooked: it cannot express a per-context database (the details
  it registers name the container's single database), and `spring.datasource.url` does **not** override it.
  Both were probed at runtime rather than assumed.
- **The two flow classes were not merged.** `PhotoApiFlowTest` asserts that an empty archive answers 404 — a
  check that deletes every photo, and through `DumpService.sixPhotosOf` a dump holding fewer than six
  answers 500, so the merged class would have to delete the dump's photos too and would stop asserting
  "upload a photo, then read it back". The criterion is met with 10 s of headroom without changing what any
  test means; the measured cost of the split is 3.9 s (`DumpApiFlowTest`'s context).

## 5. Coverage audit

Controller families, their `@WebMvcTest` slices, and the failure paths asserted:

| slice | 201/200 | 400 | 404 | 409 | 413 | 415 | 500 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `PhotoControllerTest` (9 tests) | 3 | 3 | 1 | – | 1 | 1 | – |
| `DumpControllerTest` (12 tests) | 2 | 6 | – | **1** | – | – | 1 |

`DumpControllerTest` had no 409: the concurrent-modification answer existed only in `ApiExceptionHandlerTest`
(through a probe controller) and `DumpServiceTest` (through the service), so the mapping from the dump
publish to the contract's `409 concurrent-modification` was untested end to end at the web boundary. One
test was added — `items.saveAndFlush` throwing `ObjectOptimisticLockingFailureException` — asserting status,
`application/problem+json`, `code`, `title`, `instance`, the absence of `errors` (no field was rejected) and
the word "retry" in `detail`.

Layers: unit tests with `@TempDir` exist (`StorageServiceTest`, `StorageInitializerTest`, `PhotoServiceTest`,
plus `StoragePropertiesTest`, `MultipartConfigTest`); the end-to-end flow is one class (`DumpApiFlowTest`:
six uploads over HTTP → publish → read back, on a real Tomcat, real PostgreSQL and a real data directory);
the `@DataJpaTest` slices run against the real schema with `ddl-auto=validate`.
