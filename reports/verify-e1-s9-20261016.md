## 4. What changed

`support/PostgresTestConfiguration` no longer hands Spring a `@ServiceConnection` container bean. It starts
one `postgres:17-alpine` container in a static initialiser — shared by every context in the JVM — and
exposes a `JdbcConnectionDetails` bean whose URL points at the database the context named
(`aether.test.database`, required since the review round — see §10). The database is created once per name;
PostgreSQL's `42P04` (`duplicate_database`) is the only error the creation tolerates, so two contexts naming
the same database share it.

- **One container, one database per context.** The isolation the suite had is unchanged — the flow classes
  delete every row or add a test-only Flyway migration, and either would corrupt the repository slices,
  whose assertions are about the whole archive (`DumpQueryTest` reads every dump there is, and
  `DumpService.sixPhotosOf` makes a dump that lost photos answer 500). Databases are cheap where containers
  were not.
- Seven classes name their own database with `@TestPropertySource`: the two flow classes, the two test-only
  migration classes, the two classes that boot the whole application, and — with the same name in all four,
  so the four keep sharing one context and one schema — the repository slices.
- `@ServiceConnection` was rejected, not overlooked: the connection details it registers name the
  container's single database, so a per-context database cannot be expressed through it. What the report
  measures about the arrangement is the suite itself: 13 contexts, one container, one database each
  (§3, §2).
- **The two flow classes were not merged.** `PhotoApiFlowTest` asserts that an empty archive answers 404 — a
  check that deletes every photo, and through `DumpService.sixPhotosOf` a dump holding fewer than six
  answers 500, so the merged class would have to delete the dump's photos too and would stop asserting
  "upload a photo, then read it back". The criterion is met with 10 s of headroom without changing what any
  test means; the measured cost of the split is 3.9 s (`DumpApiFlowTest`'s context).

## 8. The class-order defect, found by the review of another PR

The suite's result depended on which class ran first, and the review reproduced it from a fresh archive of
this branch. The mechanism, confirmed here before it was changed:

1. `application-test.yml` asks for `logging.level.root: WARN`, and every `@ActiveProfiles("test")` context
   applies it;
2. a Logback logger is a JVM-wide singleton, and the surefire fork is one JVM for the whole suite;
3. nothing restores the level when a context closes, so it survives every later class;
4. `DumpServiceTest` captured the service's log in a `ListAppender` and relied on the logger's *inherited*
   level being INFO. Started after any Spring class, the two tests that wait for a line saw an empty list.

Reproduced first, on the working tree, in the order that makes it fire — alphabetical puts
`AetherArchiveApplicationTests` (a Spring context) before `DumpServiceTest`:

```
$ mvn -f backend/pom.xml -B clean test -Dtest='AetherArchiveApplicationTests,DumpServiceTest' \
      -Dsurefire.runOrder=alphabetical
[ERROR]   DumpServiceTest.should_log_the_publish_only_once_the_transaction_has_committed:308
Expected size: 1 but was: 0 in:
[]
[ERROR]   DumpServiceTest.should_log_the_publish_at_once_when_no_transaction_wraps_the_call:338
Expected size: 1 but was: 0 in:
[]
[ERROR] Tests run: 18, Failures: 2, Errors: 0, Skipped: 0
[INFO] BUILD FAILURE
[INFO] Total time:  26.308 s
```

Two failures, exactly the two tests the review named.

**The fix** is in `DumpServiceTest`: the capture pins the service logger's *own* level to INFO in
`@BeforeEach` and puts back the level it found in `@AfterEach` (`Logger.getLevel()`, where `null` means
"inherited" — so a neighbour finds the logger exactly as it left it). The same command, after:

```
$ mvn -f backend/pom.xml -B clean test -Dtest='AetherArchiveApplicationTests,DumpServiceTest' \
      -Dsurefire.runOrder=alphabetical
[INFO] Tests run: 18, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
[INFO] Total time:  26.313 s
```

## 9. The suite under two class orders

Both orders are hostile, and differently so: alphabetically `DumpServiceTest` runs after the whole-application
context, reverse-alphabetically after the two `@WebMvcTest` slices — both apply the same WARN root.

| order | tests | result | Maven total | real |
| --- | --- | --- | --- | --- |
| `-Dsurefire.runOrder=alphabetical` | 280 | `BUILD SUCCESS` | 45.965 s | 48.690 s |
| `-Dsurefire.runOrder=reversealphabetical` | 280 | `BUILD SUCCESS` | 54.256 s | 56.685 s |

The 8.3 s between the two is not the tests. Per class, the reverse run only *moves* the first, most
expensive context startup from `AetherArchiveApplicationTests` (15.47 s) to `SchemaBaselineTest` (9.85 s,
the first database context in that order), with `AetherArchiveApplicationTests` itself falling to 1.10 s —
the same work in a different place, less of it in total. A second build (a security audit of this machine's
dependencies) was running while the pair ran, which is the likelier explanation for the difference; the
figure this story reports as the suite's cost is the plain `clean verify` of §2 and §11.

A third piece of evidence, because "green on my machine" is what the defect was hiding behind: the tree was
exported with `git archive HEAD` into an empty directory, the working-tree changes were applied there, and
the suite was run there under the alphabetical order that used to fail — **280 tests, `BUILD SUCCESS`,
46.033 s** (§2). That is a checkout that has never had an IDE's `target/`, another class's leftover logging
configuration, or a previous run's database anywhere near it.

## 10. The review round's other findings

- **A claim of evidence the report did not contain.** §4 used to say that the rejection of
  `@ServiceConnection` had been "probed at runtime rather than assumed"; there is no transcript in this
  report, so the claim is gone. What is left is what a reader can check: the shape of the suite — 13
  contexts, one container, one database each (§2, §3, §4).
- **The coverage table did not add up** (`DumpControllerTest` read as 10 rows for a class with 12 tests).
  Corrected in §5, with the note that the columns count test cases rather than `status()` calls — two of the
  seven 400s share `assertRejectedForPhotoCount`.
- **The 409 slice test asserted the advice's sentence indirectly.** It now also asserts that `detail`
  contains neither `ArchiveItem` nor the identifier of the row that lost the race, i.e. that the framework's
  own message — which names both — is not what reaches the body (§5).
- **Two contexts shared the default `test` database silently** (`AetherArchiveApplicationTests` and
  `MultipartUploadCeilingTest`). The default is gone: `aether.test.database` is **required**, and a context
  that boots a database without naming one fails with a message saying what to add. The failure was seen
  rather than assumed: a throwaway context that names nothing was run during this round and stopped at
  context refresh —

  ```
  Error creating bean with name 'postgresConnectionDetails' ... Factory method 'postgresConnectionDetails'
  threw exception with message: This test context boots a database but names none: add
  @TestPropertySource(properties = "aether.test.database=<name>") to the test class. Two classes may name
  the same database only when they agree to share it — neither reads a row the other wrote.
  ```

  The probe was deleted again afterwards (its class stays in `target/test-classes` until the next `clean`,
  which is the README's own advice). Both classes now name
  one (`bootstrap`, `upload_ceiling`), and the four repository slices keep sharing `repository` on purpose.
  Cost of the split: one more database, migrated once, inside the context that already boots anyway — the
  ordered runs of §9 (46–54 s) carry it.
- **The container's cleanup rested on Ryuk with nothing said about it.** The precondition is now written
  down, in the README's "Tests" section and in the configuration's javadoc: Ryuk is on by default and
  removes the container at JVM exit; with `TESTCONTAINERS_RYUK_DISABLED=true`, or a Ryuk that cannot reach
  the Docker socket, each run leaves one `postgres:17-alpine` container behind, and the README says how to
  find and remove it. No shutdown hook was added: stopping the container would hold the build for the length
  of a `docker stop`, which the 60 s budget cannot spare. Measured after four full runs of this round:
  `docker ps --filter ancestor=postgres:17-alpine` lists exactly one container — the development database —
  so the reaper did its job here.

## 11. Not changed, not verified

- **Not changed**: production code (nothing under `backend/src/main` was touched), the 13-context layout
  (§4), and the assertion of any test that already existed.
- **Not verified**: the suite has not been run on another machine or in CI — the wall times are this
  development machine's (Fedora, Docker local, warm Maven cache after the first `clean`). The first run
  inside a cold Maven cache downloads dependencies and takes longer than any figure here. The review
  measured 58.1 s for one run (a failing one), so the margin under the 60 s criterion is real and the
  numbers above are a quiet machine's.
- **One number written down twice.** The story's brief spoke of a 65 s baseline; the baseline this report
  measured is **69.0 s** (`Total time: 01:09 min`, §1). The measured figure is the one to quote.
- **Two shared invariants are named rather than assumed**: a test that captures a log pins the level it
  needs, and a context that boots a database names it (§4). Neither is enforced by the compiler; both fail
  loudly when broken, and both can be exercised with the two `-Dsurefire.runOrder` runs above.
