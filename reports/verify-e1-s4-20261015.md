## 3. The container's upload ceiling matches the service's

The service counted bytes, but `spring.servlet.multipart.max-file-size` was still Spring's 1 MB default —
Tomcat would have refused a legitimate 5 MB upload before `StorageService` ran, making the documented
`AETHER_MAX_UPLOAD_MB=15` a lie at the HTTP boundary. Both keys now reference the same property, and the
context test pins them:

```
@Value("${spring.servlet.multipart.max-file-size}")     ==  storageProperties.maxUploadMb() + "MB"
```

**PASS** — and unwiring it fails the build instead of silently regressing to 1 MB.

## 4. Symlink policy (carried over from the E1-S2 finding)

`StorageService` resolves the data root, `images/` and `tmp/` with `toRealPath()` before every write and
refuses a destination that does not stay inside the tree. An `images/` symlinked **outside** the data
directory is therefore refused with an actionable error rather than quietly writing the archive outside its
own backup set; a link that stays inside is accepted, and the data directory itself may be a symlink. Both
branches are tested. Recorded as an amendment to ADR-012.

## Verdict

**Not covered / SKIPPED**

- **No HTTP upload path yet**: the endpoint arrives in E1-S6, so multipart requests were not exercised
  end-to-end. This is the one place a container-level refusal (`MaxUploadSizeExceededException`) will appear,
  and E1-S8 maps it to a problem detail.
- **`ProblemDetail` responses**: refusals carry a stable `code` (`unsupported-image-type`, `upload-too-large`,
  `storage-failure`) but no HTTP mapping exists until E1-S8 — the acceptance criterion that names a
  `ProblemDetail` is satisfied at the API layer in that story.
- Only the **signatures** of the formats are exercised, not real payloads: the archive never decodes an
  image, so there is nothing else to check.
- The read-only-directory test self-skips under root; it ran here and is not skipped in practice (uid 1000).
