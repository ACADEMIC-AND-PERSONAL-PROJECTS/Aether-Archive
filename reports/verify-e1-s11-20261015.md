## 1. Compose file validates, and `.env` really drives it

```
$ docker compose -f docker-compose.dev.yml config | grep -E 'published|host_ip'
        host_ip: 127.0.0.1
        published: "5432"

# with AETHER_DB_PORT=55432 in .env (temporary):
$ docker compose -f docker-compose.dev.yml config | grep -E 'published'
        published: "55432"
```

**PASS** — the file parses, the port is bound to loopback, and a value in `.env` overrides the built-in
default (so the documented "edit `.env`" workflow is real, not decorative). `.env` was restored to the
`.env.example` values afterwards.

## 2. Container starts and reports healthy

```
$ docker compose -f docker-compose.dev.yml up -d
 Volume aether_pgdata Created
 Container aether-db Started
$ docker inspect --format '{{.State.Health.Status}}' aether-db      → healthy (after ~6 s)

$ docker compose -f docker-compose.dev.yml ps
NAME        IMAGE                SERVICE   STATUS                    PORTS
aether-db   postgres:17-alpine   db        Up (healthy)              127.0.0.1:5432->5432/tcp
```

**PASS** — the `pg_isready` healthcheck gates on a database that actually accepts connections.

## 3. The documented credentials work

```
$ docker compose -f docker-compose.dev.yml exec -T db psql -U aether -d aether -tAc "select current_database()||' | '||current_user||' | '||version();"
aether | aether | PostgreSQL 17.11 on x86_64-pc-linux-musl, compiled by gcc (Alpine 15.2.0) ...
```

**PASS** — database, user and version come back for the `POSTGRES_*` values documented in `.env.example`.

## 4. Reachable from the host, invisible to the LAN

```
$ bash -c "echo > /dev/tcp/127.0.0.1/5432"         → open   (expected)
$ bash -c "echo > /dev/tcp/192.168.1.10/5432"      → closed (expected: loopback-only)
```

**PASS** — the archive database is reachable only from this machine. Binding to `0.0.0.0` would have put it
on the LAN; the compose file pins `127.0.0.1` for that reason.

## 5. Data survives a stop/start cycle

```
$ psql … "select system_identifier from pg_control_system();"   → 7697004199025942562
$ docker compose -f docker-compose.dev.yml down        # volume kept
$ docker compose -f docker-compose.dev.yml up -d       # → healthy
$ psql … "select system_identifier from pg_control_system();"   → 7697004199025942562
```

**PASS** — the same PostgreSQL cluster comes back, so `aether_pgdata` really is durable and `down` (without
`-v`) does not lose the archive. (A cluster identifier is used instead of a test table because `DROP TABLE`
is guard-blocked in this repository — no junk is left behind.)

## Verdict

**GREEN** for everything the story can verify at this point in the sprint.

**Not covered — deferred to E1-S3, deliberately**

- **`./mvnw spring-boot:run` connecting to the database.** The backend has no JDBC driver, datasource or
  Flyway until E1-S3, so the application cannot open a connection yet; the criterion is verified in that
  story, on top of the evidence above (host port reachable, documented credentials authenticated).
- **`.env` is not read by Spring Boot yet.** Compose reads the file directly; the backend reads real
  environment variables. The dev-flow bridge (`spring.config.import`) is specified for E1-S3, and the docs
  now say exactly that instead of implying a mechanism that does not exist.
- No `.env` is committed (gitignored); the value `POSTGRES_PASSWORD=change-me-local` in `.env.example` is a
  documented placeholder, and the port is loopback-bound, so it is not a credential for anything reachable.
