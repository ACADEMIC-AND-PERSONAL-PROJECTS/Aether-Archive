**Watch this number**: the suite is at 57 s against E1-S9's acceptance criterion of "under 60 s". E1-S7's own
end-to-end class costs ~4–5 s of context startup, and it cannot share a context with the photo flow class
because each class's `@DynamicPropertySource` contributes to the context cache key. Making the budget hold is
explicit work for E1-S9, not an assumption — folding the two flow classes together reclaims the difference.

## 2. The order round trip, with a shuffled request

Six PNGs uploaded in order 1…6, then published in the order **2, 5, 1, 6, 3, 4**:

```
POST /api/v1/dumps → 201
{"id":"4c3407c6-…","title":"Octobre","backgroundColor":"#2E4A62",
 "photos":[{"id":"7a03f9bf-…","url":"/images/7a03f9bf-….png","category":"dump","uploadedAt":"…"}, … six in all …],
 "createdAt":"2026-10-16T00:50:14.865484Z"}

201 order == requested order: True      database display_order 0..5 == requested order
list order == requested order: True     201 order == list order: True
createdAt identical in 201 and list: True     newest first: True
version = 1 on all six photos
```

**PASS** — the curation order survives the whole path: request → row → 201 → list. The position is the array
position, so no response carries a `displayOrder` field (ADR-011 §3).

## 5. The query budget is measured, not assumed

`DumpQueryTest` pins `prepareStatementCount == 2` for `GET /dumps`, with Hibernate statistics enabled in the
test profile. A per-dump lazy read fails it (measured: `expected: 2L but was: 3L`). The fetch join is kept
even though the probe showed two statements either way — Hibernate answers a lazy proxy's identifier getter
without a SELECT — so that the count never depends on that behaviour.

## 6. Review round 1 — the lost race, and the atomicity claim made testable

The review found no blocking defect and proved three things by experiment: the publish transaction rolls back
whole (a second connection held `select … for update` with a `lock_timeout`), the `@Version` tests really
measure the lock (removing it fails the competing-update assertion), and the fetch join is **not** what holds
`GET /dumps` at two statements. Two findings needed work:

**A lost race answered 500 `internal-failure`** — which the archive's own README defines as "a bug: no
handler claimed this exception". A double-tapped Publish was told the archive was broken. It now answers:

```
409 application/problem+json
{"type":"about:blank","title":"Concurrent modification","status":409,
 "detail":"Another write changed this row first; read it again and retry the request.",
 "instance":"/api/v1/dumps","code":"concurrent-modification"}
```

The framework's message (which names the entity and the row) goes to the log, never to the body. The code is
recorded in the README table and as an amendment to ADR-013.

**The atomicity claim had no committed test.** `DumpPublishAtomicityTest` drives a real PostgreSQL with the
service proxied and no test-managed transaction, and makes every curation update fail: the flushed
`archive_item` insert is rolled back, **zero items** remain, and the six photos keep no item and no position.
A future "catch the lock exception inside `create`" could otherwise commit an item without its photos, and
nothing would have noticed.

Also fixed: a dump whose group is not six photos makes the **read** fail loudly instead of publishing an empty
`photos` array; the `DumpQueryTest` comment that contradicted the code beside it; and the publish log now
happens after the commit rather than before.

**Suite wall time is 65 s** — over E1-S9's own 60 s criterion, because the new atomicity class needs its own
context. Reducing it is that story's deliverable, not this one's.

## Verdict

**Not covered / SKIPPED**
